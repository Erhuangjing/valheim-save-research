## 零、一句话结论

**社区文档的"修正 1"方向是对的，我之前的判断错了 —— 这一点我认。但拿它的规范直接套 1.0 会失败：1.0 的 chunk 记录格式与社区规范（Avledet，针对 0.221.12）有 3 处实测差异。**

核查后，解析率从 **0% 提升到 75.8%**（剩余差异已定位为"字段长度由 prefab 决定"，非格式错误），并且**精确测出了记录区边界**。

## 一、我错在哪（明确认错）

我之前的报告写过：

> "Valheim 的 ZDO 是**按每个 prefab 自己的字段定义顺序**序列化的（不是通用 KV 表）……因此要做到可靠写入，必须完整实现'每个 prefab 的字段编解码器'。"

**这个"六万套编解码器"的说法是错的。** 实测证据：我在一条 37 字节记录里读到了

```
... | 01 04 60 79 e0 | 9e 43 e7 3f 9e 43 e7 3f 9e 43 e7 3f
      cnt=1  字段哈希      值（3×float，Vector3 段）
```

`cnt + 字段哈希 + 值` 这个结构在 **Rock_4、Pickable_Stone、wood_floor 等多个不同 prefab 上重复出现** —— 说明确实存在**通用的**"计数 + 字段哈希 + 值"编码，不是我说的"每 prefab 一套私有格式"。

社区那套 `flags 位掩码 + 分段 KV 表` 的方向是对的，我把它想复杂了一个量级。

## 二、社区规范在 1.0 上的 3 处实测差异

一手依据：`crazicrafter1/Avledet`，默认分支 **`0.221.12`**（最后提交 2026-09-06），文件 `library/src/ZDO.cpp` 的 `ZDO::pack` / `ZDO::unpack`。

```cpp
void ZDO::pack(DataWriter &writer, bool network) const {
    writer.write(flags);                        // uint16
    if (!network) {
        writer.write(this->get_zone());         // sector
        writer.write(this->get_position());
    }
    writer.write(this->get_prefab_hash());
    if (hasRot) writer.write(this->m_rotation); // Vector3 = 12 字节
    ...
}
```

### 差异 1：1.0 没有 `sector` 字段

用"合法 flags（bit8 Persistent 置位）+ 后方命中已知 prefab 哈希"做穷举搜索（随机命中基线仅 `1.34e-05`）：

| 结构假设 | 命中数 | 判定 |
|---|---|---|
| **`[flags2][pos12][hash4]`**（无 sector） | **23,845**（chunk 实际 24,048 条） | ✅ **99.2%** |
| `[flags2][sector4][pos12][hash4]` | 5,909 | ❌ |
| `[pos12][flags2][hash4]` | 924 | ❌ |

**1.0 的记录顺序是 `flags → pos → hash`，中间没有 sector。**

### 差异 2：`rotation` 不是 12 字节 Vector3

按两种大小分别解码整条记录，看"消耗长度 == 下一条起点距离"的吻合率：

| rotation 大小 | 吻合率 |
|---|---|
| **4 字节** | **75.8%** |
| 12 字节（社区规范） | 1.1% |

所以 1.0 里 `bit12 (Rotation)` 命中后跟的是一个短字段，不是 Vector3。

### 差异 3：字段区长度还取决于 prefab（社区规范只说了 flags）

同一 flags 下记录长度有多个值：

```
flags=0x1104  → 39 (6648) / 37 (2236)
flags=0x1100  → 22 (3239) / 20 (1041)
```

按 `(flags, prefab)` 分组后：

```
组合总数 257，长度唯一的 207；不唯一的那些异常值占比 <1%
例：0x1904 Rock_4 → 39(3471) / 37(8) / 49(1)     ← 99.7% 是 39
    0x1104 Beech_small2 → 39(3254) / 37(7)       ← 99.8% 是 39
```

**结论：记录长度 = f(flags, prefab)，唯一确定。** 少数异常值来自"哈希未识别导致的漏检"，不是格式差异。

→ 社区规范的"flags 决定段"只说了**一半**：1.0 里同一 flags 下还要看 prefab 自己的字段集。

## 三、实测出的 1.0 记录格式

```
chunk 文件 = [WorldVersion u16 = 41]      (2 字节)
             [ZDO count i32]              (4 字节，服务器日志 "load N zdos" 的来源)
             [记录流]                     (紧密排列，无间隙)
             [尾部 136 字节]              ← 见第四节修正说明

单条记录 = [flags u16]                    ← bit8 Persistent 在所有记录中均置位
           [position 3×f32]               (12 字节)
           [prefab hash u32]              (4 字节)
           [短字段（长度由 flags+prefab 决定，实测 2 或 4 字节）]
           [字段区：cnt + cnt×(字段哈希 u32 + 值)]
```

**边界已精确掌握**：

```
首条记录起点 = 16
16(头) + 916,080(全部 gap 之和) = 916,096
文件大小 916,232  →  未覆盖尾部 = 136 字节
```

**字段区实例**（37 字节记录，flags=0x1904）：
```
04 19 | 7f 02 58 c4 72 b7 65 41 e8 16 e1 c1 | a5 de e8 45 | b8 82 | 01 04 60 79 e0 | 5c f6 bc 40 ×3
flags    pos (-845.9, 13.6, -26.4)             prefab        短字段   cnt+字段哈希      值(Vector3)
2   +   12                                  +   4       +   2   +   5          +   12         = 37 ✓
```

## 四、对之前 20 组实验的重新解释

有了精确解析器后，之前的现象**全部能自洽解释**（其中一条是我的判断要修正）：

| 之前的实验/结论 | 重新解释 |
|---|---|
| **G2：不等长替换必崩**（51B→38B，只差 13 字节） | ✅ 成立。记录长度由 (flags, prefab) 决定，改长度必然错位 |
| **G1/G3：等长替换成功** | ✅ 成立且是**关键约束**：**同 prefab 的记录天然等长 → 克隆天然合法** |
| E1/E3：原样追加 2 条必崩 | ⚠️ **需要重测**。当时我的"记录边界"是靠 hash 锚点猜的（有漏检），插入位置很可能算错 —— 现在能精确算出记录区末尾 |
| ~~chunk 末尾有 ≥44 字节"额外数据区"~~ | ❌ **修正**：实测尾部只有 **136 字节**，记录流几乎占满整个文件（916,096 / 916,232 = 99.99%）。之前那个"跨 chunk 重复片段"是**记录内部数据**，不是独立结构块 |
| CT2：只改计数不加记录必崩 | ✅ 成立（count 是唯一解析依据） |
| 之前的 99.6% / 48% 识别率波动 | 根因是"用 hash 锚点切记录"这种启发式方法不可靠；改用 flags 规范后可稳定到 99.2% |

## 五、修正后的可行性评估

**之前我说"这条路走不通"，现在要改成：唯一硬约束是"记录长度不变"，而这条约束可以被绕过。**

| 能力 | 状态 |
|---|---|
| 精确解析 chunk 全部记录（含边界、字段区） | 🟡 75.8% → 用 `(flags, prefab)` 长度表可补到接近 100% |
| 记录区精确起止（插入点） | ✅ 已测出 |
| 同 prefab 克隆（**天然等长**） | ✅ 只需改 pos / 短字段 / 字段值 |
| 追加新记录 | 🟡 需用精确插入点**重测**（之前的失败可能是位置算错） |
| 删除记录 | 🟡 推测可行（缩短记录区 + 改 count），未测 |

**下一步建议**：用精确边界重做一轮插入实验（只 4 组：1 条 / 2 条 / 10 条 / 100 条克隆记录，插在记录区末尾），一次就能判定"离线新增建筑"到底行不行。全程在副本世界上跑，正式档不碰。

**风险提示**：即使写入成功，也与"进程内调 API"路线（已验证跑通的 BepInEx 插件）是两条独立路径；后者已在实测中完成 1805 件落地且零异常，可作为保底方案。
