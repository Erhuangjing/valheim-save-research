## 二、1.0 容器格式（本轮实测解出）

### 2.1 chunk 文件 —— **没有压缩**

```
[WorldVersion u16 = 41][ZDO count i32]      ← 头只有 6 字节
[记录流]                                     ← 紧跟其后；中间夹杂"非 ZDO 数据块"
[尾部 2 ~ 136 字节]
单条记录 = [flags u16][position 3×f32][hash u32][rot?][conn?][字段区]
```

对照三个时间点：

| 文件 | 字节数 | chunk 头 count |
|---|---|---|
| `20_1e__1_41.chunk`（20:39 备份） | 987,129 | 25,316 |
| `20_1e__1_46.chunk`（22:46 备份） | 988,839 | 25,165 |
| `20_1e__1_48.chunk`（22:48 最终） | 982,759 | 25,035 |

锚点法（`flags & 0x0100` 且 `p+14` 命中 prefab 哈希库）识别出 24,813 / 25,035 条，**识别率 99.11%**。

> 修正此前文档的推断："98 万字节无明文浮点数组 → 所以是压缩存储" —— **错的**。
> chunk 完全没压缩，明文 prefab 哈希满文件都是。真实原因是地形块本身是二进制/位图编码。

### 2.2 `_main.xx.chunks` = zone 索引表（164 字节）

```
[ver u16][全局 ZDO 总数 u32][zone 数 u32]
每条 11 字节: [zoneX u8][zoneZ u8][verMajor u8][verMinor u8][00 00 00][count u32]
```

14 条 = 14 个 chunk。条目里的 `verMajor_verMinor` 与 `.chunk` 文件名里的 `1_48` **完全对应**，
`count` 与 chunk 头的 count 一致。注意条目里的 zoneX/zoneZ 与文件名是 **x/z 互换**的。

### 2.3 `_main.xx.db2` = gzip 压缩的全局静态结构注册表

从 off=16 起是 gzip，解压 215,487 字节 / 930 条锚点。内容是**世界生成期的静态结构**：
`SunkenCrypt4`、`GoblinCamp2`、`Mistlands_Statue1`、`Greydwarf_camp1`、`Mistlands_RoadPost1` …

这些记录的 `position` 是 `(1580, 0, 0)` 这类**索引值而非世界坐标** → db2 是注册表，不是空间数据。

### 2.4 `_main.xx.fwl2` = 世界元数据（2050 字节）

名字 `WORLD`、世界 ID。装不下地形。

## 四、定位地形块的方法："锚点间隔异常"

1. 找锚点：`flags & 0x0100` 且非 `0x8000`，`p+14` 处 u32 命中 prefab 哈希库，坐标合理。
2. 相邻锚点间隔中位数 **39 字节**；**间隔 ≥ 120 字节的位置之间就是非 ZDO 数据块**。
3. 主宅 zone 里最大块 **10,921 ~ 10,971 字节**，坐标全集中在玩家改造过地形的位置。

## 六、附带发现

1. **22:46 → 22:48 主宅 zone 少了 221 条对象**：`wood_floor_1x1` ×54、`wood_pole` ×13、
   `wood_beam` ×12、`Wood` ×24、`Coal` ×11 …；新增 93 条（动物/鱼/肉）。
   → 这 54 块地板 + 柱子梁的消失，很可能就是用户说的"房子开始崩塌"，建议单独追。

2. `position = (1000000, 0, 1000000)` 是 Valheim 的**"无位置"哨兵值**，这类记录会被常规坐标过滤掉。
   `00_00__0_12.chunk`（1,484 B = 头 6B + 82 条 × 18B）整份都是这种记录，
   `flags=0x0100`、`hash=0x65835e28`（该哈希在 54 万个游戏字符串里反查不到，未解）。三个时间点完全一致。

3. 1.0 存在 **bit13** 置位的记录（如 `flags=0x2100`），社区文档只定义到 bit12。

4. `rot` 字段实测是 **2 或 4 字节**，不是社区规范里的 12 字节 Vector3。
