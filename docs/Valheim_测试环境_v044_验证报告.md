## 一、本轮定位到的三个真 bug

### Bug 1（致命）：残留锚点让整栋下沉 3.38 米

```
09:26:24  [地形] ★ 基准 H_base = 42.43
09:26:25  [落地] ★ 使用 bp_anchor.txt 记录的建造基准 Y = 39.0464
09:26:25    ⚠ 本次地形算出的基准 42.4306 与锚点相差 3.384 米（以锚点为准）   ← 警告被无视
```

后果：整栋埋进地形 3.38 米 → 件向下的支撑射线起点落在碰撞体内部 → 判定无支撑 →
持续掉血消失。件数一路 1805 → 1653 → 1635，支撑下限 1000 → 20.6 → 10.4。

**这正是正式服「走开再回来房子塌了」的机制**：件埋在土里，一直在掉血。

修法：
- 优先级改为 **本次地形基准 > 锚点文件 > 现场采样**（地形真跑过时它就是当前真值）
- 锚点文件增加 `originX/originZ` 归属校验，与当前落点差 > 0.5 米即判为残留并忽略

### Bug 2：多任务流水线没有串行

```
09:26:25  [地形] 完成
09:26:35  ★ 落地完成：共 1805 件
09:26:52  === 清理废弃建筑 ===        ← 清理比落地晚 17 秒
09:27:25  [清理] 完成：共搬走 972 个物件
```

原因：清理要「等激活 + 等 zone 长出自然物」，天然晚 40~100 秒启动；
而地形/落地只等 `s_placeDone`，没等清理 → 三者各跑各的。
清理的匹配规则是「前缀白名单 + 区域兜底」，白名单里的 `wood_floor / stone_wall`
和房子构件同名，跑在落地之后就有吃掉房子的风险。

修法：阶段闸门 **激活 → 清理 → 地形 → 落地**，每个任务等前一个；
所有提前 `yield break` 出口补放行标志（否则死锁）；闸门带 6 分钟超时。

> 附：事后核对证明**这一次清理并没有吃掉房子** —— 清理第 1 轮只命中 52 个
> （`xiabp` 标记保护生效），角落里的蓝图构件数在事件前后都是 3233（零增长）。
> 但时序本身仍是必须修的隐患。

### Bug 3：对账用精确 key，导致每次启动重复补件

| 版本 | key 方案 | 结果 |
|---|---|---|
| 初版 | hash + 位置(0.25m) | 一件满足多件期望 |
| v0.25 | + yaw(90° 四档) | 45°/135° 档边界抖动，误判 +34 件 |
| v0.25.1 | yaw 细化到 1° | **仍误判 48 件**（1805 → 补成 1853） |
| **v0.44.1** | 不用 key，见下 | **缺失 0** ✓ |

根因：期望侧 yaw 是蓝图里的干净值（270.0），实际侧是
`Quaternion.Euler` → ZDO → `eulerAngles.y` 读回，中间一次四元数往返得到
269.9998 / 270.0001。**任何量化都有边界，有边界就会抖动。**

修法：改成「同 prefab + 空间容差（水平 0.8m / 垂直 1.6m）最近邻 + `used[]` 一对一消耗」，
**完全不比较朝向**。顺带解决蓝图里 24 组「同 prefab、位置差 0.02~0.08 米」的成对构件错配。

## 三、剩余的唯一问题：蓝图自身的结构弱点

关掉支撑保险（跑真实支撑计算）时，**稳定只丢 10 件，全部是 `stone_arch`**：

| 项 | 值 |
|---|---|
| 数量 | 12 个石拱门排成一列（py −1.674，地表下约 1 米的拱廊） |
| 存活 | 只有最西端 2 个挨着石墙的 |
| 复现性 | **正式服与测试服丢的是完全同一批** |

判定方法：**看丢失集合是否可复现**。恒定丢同一批 → 蓝图结构问题（作者多半在无支撑限制下建的）；
随机丢、位置飘 → 落位/地形 bug。

处置：靠支撑保险锁定 `Support.Enabled=true`（当前测试服就是这个状态，实测 1805 稳定）。
要彻底根治（无模组客户端也稳），需要把所有权钉在服务器端（拒绝 `ZDO.SetOwner` 把 owner 转给客户端）。
