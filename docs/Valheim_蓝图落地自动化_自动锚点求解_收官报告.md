## 1. 本轮做了什么：把 `YOffset` 从「手动试错」变成「自动求解」

### 1.1 原理（前八轮已闭环的机制）

`WearNTear.UpdateSupport` 里「件 → 件」的支撑传递是**乘性衰减**：

```csharp
num3 = Mathf.Max(num3, support2 - horizontalLoss * 距离 * support2);   // support × (1 − loss × 距离)
```

链一长就指数衰减，实测最小 support 被压到 **21.7**。而材料下限差 10 倍：

| 材料 | 最大 support | **下限 GetMinSupport()** |
|---|---|---|
| 木构件 | 100 ~ 140 | **10** |
| 石构件 | 1000 ~ 1500 | **100** |

所以石构件在链尾跌破下限被当帧满血销毁，木结构一件不掉。
**链条的起点是「地面锚点」**（包围盒碰到 terrain 的件）——锚点少，链就长，尾部就死。

### 1.2 做法：不猜 GroundLayerPy，直接算 d_i

落地完成后，对每一件求：

> **d_i = 「这一件下沉多少米，它的包围盒才会碰到地形」**

判定完全复刻游戏自己的那套（`WearNTear.UpdateSupport` 845 / 870 / 902 行）：

```csharp
Physics.OverlapBox(包围盒中心下移 d, bounds.size / 2 + 0.15) 命中 terrain 层
```

那个 `0.15` 就是 WearNTear 自己加的余量，也正是「硬边界」的宽度。

把 `d_i` 排序就得到**完整的 `anchorCount(d)` 累积曲线**，一步到位知道"下沉多少能拿到多少锚点"。

### 1.3 关键设计：闭环，因为「预测 ≠ 实测」

第一版是单发求解。实测：

```
预测 298 个锚点 → 实选 1.20 米 → 实测只有 256（目标 259）→ 目标落空、多丢 1 件
```

**差 42 件。** 于是改成实测驱动：每轮都以「真实测出来的锚点数」为准，不达标就基于**当前实际位置**再求一轮，最多 3 轮。

实测收敛过程（R16，Target=200）：

```
第 1 轮：实测锚点 33  → 目标 200 → 下沉 0.40 米
第 2 轮：实测锚点 221 → 达标 → 停止
★ 求解结束：累计下沉 0.40 米，锚点 33 → 实测 221 ｜ 总耗时 2.3s
```

**全程 2.3 秒。**

### 1.4 还必须有一个「手术窗口」

这里有个先有鸡还是先有蛋的死结：

- 件必须先**被实例化**才能量几何 → 实例化要求 refPos 指过来（也就是激活）；
- 可一旦激活，`UpdateWear` 立刻开算 → 地基那层先掉 29 件，几何也从此量不准。

**解法**：放行激活**之前先把磨损冻上**（`Harmony` prefix 跳过 `UpdateWear`），
让件活过来但不参与判定。求解 + 整体位移都在这个「零销毁干扰」的窗口里做完，做完再解冻。

```
落地完成 → 等件实例化（4633 件，2 秒）→ 等清理完成 → 实测求解 → 整体下沉 → 复测 → 解冻
```

## 2. 最有价值的发现：**锚点数不是越多越好**

> ⚠️ **本节的结论后来被推翻了。** 真正的判据是「必死件数」，不是锚点数 ——
> 见**第 8 节**（R17~R19）。本节保留下来是为了记录推理路径：
> 正是「锚点 604 反而输给 221」这个反常现象，把线索指向了地形的薄壳特性。

这是本轮最反直觉、也最值钱的一条：

| 下沉量 | 锚点数 | 丢失 | 来源 |
|---|---|---|---|
| 0（基线） | 33 | **36** | R2 |
| 0.25 | 41 | 29 | R5 |
| **0.40** | **221** | **0** ✅ | **R16（自动）** |
| 1.00 | 196 | 0 | R8（手动） |
| 1.25 | 264 | 1 | R11~R15（自动，目标 259） |

**下沉 1.25 米（锚点 264）反而丢 1 件，下沉 0.40 米（锚点 221）却是 0。**

原因推断：下沉过头会让底层件**穿进地形凹坑**（地窖口、沟槽），
反而从"咬住平台表面"变成"悬在凹坑上方"。锚点总数变多了，但那几件却失去了支撑。

**所以判定标准不是「锚点越多越好」，而是「锚点数够用就好」——甜区约 200~220。**

配置就一行：

```ini
[Anchor]
## 0 = 自动取「可能够到地形的件数 × 0.40」（本例会算出 259，过头）
## 200 = 实测甜区，收敛到 0.40 米下沉、锚点 221、零丢失
Target = 200
```

清理代码有三处问题，逐条修掉：

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | **时机错了** | 清理跑在世界加载后、激活前，此时落点 zone 根本没加载，自然物还没被 zone 系统生成出来 —— 扫 83145 个 ZDO 只命中 43 个 | 加 `Cleanup.WaitActivate`：等 `refPos` 覆盖生效后再等 24 秒，让 zone 长齐 |

| 3 | **判据错了** | 依赖名字白名单，但**本地自然物不在 ZNetScene 的网络 prefab 表里**，`GetPrefab(hash)` 返回 null → 名字为空 → 永远匹配不上 | 加 `Cleanup.ClearAllInArea`，默认 `true`：区域内一律清（玩家/墓碑/传送门/本插件的件仍永久保护） |

```

另外把清理轮次上限从 15 提到 60（zone 会持续分批生成新对象，15 轮清不完）。

**但最后证明：那块 `Stone` 不是真凶。** 它其实不在运行时 ZDO 集合里（只是存档里的残留记录），
既清不掉也不会实例化碰撞体。真正的原因在下一节。

## 8. 追加：为什么「锚点数」是错的指标（R17~R19）

### 8.1 地形是薄壳，所以每件都有一段「接地窗口」

`R17` 加了一个逐件位图诊断（扫描 0~1.5 米的每一档，记录盒内有没有地形），结果完全颠覆了之前的理解：

```
0.0m:33(-613)  0.2m:41(-605)  0.4m:221(-425)  0.6m:221(-425)
0.8m:196(-450) 1.0m:197(-449) 1.2m:256(-390)  1.4m:604(-42)
```

括号里是「上一档还接地、这一档就不接了」的件数 —— **每档都有 400~600 件**。

根因：**Valheim 地形的碰撞体是高度场薄壳（mesh 表面），不是实心体**。件的包围盒半高约 `size.y/2 + 0.15`，于是每件都有一段「接地窗口」：

| 盒体位置 | 判定 |
|---|---|
| 完全在地表**上方** | 不接地 |
| 与地表**壳相交** | **接地** ✅ |
| 整个沉到地表**以下** | 又不接地 |

**窗口宽度 ≈ 该件的盒体高度。** 扁平件（石地板/石基础）窗口最窄、最容易踩空 ——
这正是"崩塌永远发生在石基础"的真正原因。

### 8.2 于是整体位移是个零和博弈

诊断清单里抓到了那个反复丢失的件：

```
stone_floor_2x2 @(-261.0, 39.75, 275.9)  首次接地 d=0.00m，但下沉 1.40m 时盒内已无地形
darkwood_decowall @(-261.5, 38.75, 274.9) 首次接地 d=0.00m，但下沉 1.40m 时盒内已无地形
wood_floor @(-261.0, 40.25, 271.9)        首次接地 d=0.35m，但下沉 1.40m 时盒内已无地形
```

**它原地（d=0）本来接地** —— 是我们的下沉动作把它推坏的。
而 `wood_floor` 那批反过来，**必须下沉 0.35 米才接地**。

**所以不存在一个下沉量能照顾所有件。** 整体位移只能挑「坏得最少」的那一档。

### 8.3 正确的判据：必死件数，不是锚点数

R18 试了「选 anchorCount 曲线的峰值档」：下沉 1.40 米拿到 **604 个锚点**（首个达标档 0.40 米只有 221），
**结果反而丢 1 件** —— 锚点数是错的指标。

真正的判据是 **必死件数**：盒内**既无地形、又无别的构件、又无其它物体**的件。
这对应 `UpdateSupport` 里 support 归零那条路（870/902/951 行），是**绝对必死**的（当帧满血销毁）。

实测每一档的（锚点数 / 必死件数）：

| 下沉量 | 锚点数 | **必死件数** |
|---|---|---|
| 0.0 m | 33 | **0** |
| 0.2 m | 41 | **0** |
| 0.4 m | 221 | 133 |
| 0.6 m | 221 | 283 |
| 0.8 m | 196 | 299 |
| 1.0 m | 197 | 359 |
| 1.2 m | 256 | 407 |
| 1.4 m | **604** | **526** ← R18 选的"峰值"恰是必死最多的档 |

**锚点数完全非单调（604 后面还能掉到 300），必死件数却单调递增。**

### 8.4 R19：自动选档，再次零丢失

改成「选必死件最少的档，并列时取锚点多的」，插件自动收敛到 **0.45 米**：

```
第 1 轮：必死 0 件、锚点 41  → 下沉 0.20m
第 2 轮：必死 0 件、锚点 221 → 下沉 0.20m
第 3 轮：必死 0 件           → 停止
★ 累计下沉 0.45 米，锚点 221｜离线复核 存活 4625/4625，丢失 0
```

**这一次不需要手填任何参数** —— 判据本身把答案推出来了。

### 8.5 完整的损失模型

```
总损失 = 必死件（盒内三者皆无） + 链尾件（有支撑但链太长、support 跌破材料下限）
```

下沉量与两者是反向的：

- 下沉 ↑ → 盒体沉到地表壳以下 → **必死件 ↑**
- 下沉 ↑ → 支撑链变短 → **链尾件 ↓**

两者相抵，存在最优档。这也解释了为什么 R8（1.0 米）和 R16（0.40 米）都能 0 丢失，
而 1.25 / 1.40 米会丢 —— 后者落在"必死件已经涨起来"的一侧。

### 8.6 还没做完的

「必死件」判据目前**只覆盖了 `UpdateSupport` 的盒体路径**，漏掉了件对件支撑的
`FindSupportPoint` 射线路径（995–1007 行，只用于件与件之间）。
所以这个数被高估了 —— 实测"必死 133 件"的那一档仍然 0 丢失。

把两条路径合并进判据，才能得到真正精确的损失预测。这是下一轮的事。

## 9. 通用化第一步：消灭两个手填参数（R20~R23）

目标很清楚 —— 之前这套流程**绑死在「usagi + 这块地」上**，因为有两个数字要我手敲：

| 手填项 | 含义 | 后果 |
|---|---|---|
| 落点坐标 `(-262, 270)` | 房子盖在世界哪个位置 | 换块地就得重新量 |
| `GroundLayerPy = -1.60` | 地板离地面多高 | 猜偏了要么悬空要么埋太深 |

### 9.1 自动算 GroundLayerPy：关键是跳过「孤立低层」

第一次尝试用「最低的够密档（阈值 max(4, 件数/100)）的 py 中位数」，算出 **-1.10** —— 然后丢了 7 件。

看 usagi 的真实 py 分布才明白为什么：

```
档 -6  py∈[-3.00,-2.50)    8 件   darkwood_decowall×8   ← 孤立（-2.5~-2.0 是空的）
档 -4  py∈[-2.00,-1.50)    1 件   stone_floor_2x2×1     ← 与 -1.50 档连续
档 -3  py∈[-1.50,-1.00)   80 件   wood_floor×24...      ← 中位数 -1.10，被这个算法选中
```

- 取 `min(py)` = **-2.60** → 整栋抬高 1 米，全悬空
- 取「够密档中位数」= **-1.10** → 地基多埋 0.5 米，实测丢 7 件
- 取 **-1.60** → 0 丢失 ✅

`-1.60` 那一层**只有 1 件**，但它和上面的 `-1.50` 档是**连续的**；而 `-2.60` 那 8 件上方是空的，是**孤立层**。

**所以正确判据是：从最低档往上，跳过孤立低层（与上方最近非空档之间隔着空档），取第一个非孤立档的最小 py。**

```
[基准]   跳过孤立低层 py∈[-3.00,-2.50)（8 件；上方 -2.50~-2.00 为空）
[基准] 无 wood_fence → 回退 py 直方图：自动 GroundLayerPy = -1.60（最低非孤立档 py∈[-2.00,-1.50) 共 1 件）
[基准] 覆盖手填值 -1.10 → -1.60（差 -0.500 米）
```

判别性验证：故意把配置填成 `-3.00`，插件照样算出 **-1.60** —— 手填参数被彻底消灭。

> 说明：插件原本就有「从院墙 `wood_fence` 反推地面层」的检测，但 usagi **没有院墙**，
> 所以那条路走不通、只能手填。现在补上了「无院墙 → py 直方图」的回退路径。

### 9.2 位移改成双向（±2 米）

原来只能下沉（0~1.5 米）。但既然每件都有一段接地窗口，**最优档完全可能落在原位上方**，
单向搜索会漏解。改成 `[-MaxShift, +MaxShift]` 双向搜索（内部仍用 0..2N 的递增索引，
只在算位移时减掉 maxSteps），默认 ±2 米。

### 9.3 并列时取「下沉更深」的那一档

R22 的档位表暴露了最后一个问题：

```
0.0m:221/死0    0.1m:221/死0    0.3m:220/死129
```

两档的必死件都是 0、锚点数都是 221，判据停在了先碰到的 `0.00` —— **丢 7 件**。
如果多沉那 0.1 米，累计正好到 0.45 米，就是 R19 零丢失的位置。

**判据从「并列取先遇到」改成「并列继续往深走」**（`>` → `>=`）。理由是：
接地效果完全相同时，埋得更实的那一档支撑链更短、更稳。

### 9.4 结果：全自动，零手填

```
[基准] 跳过孤立低层 → 自动 GroundLayerPy = -1.60
[锚点] 第 1 轮位移 0.25 米（必死 0、锚点 41）
[锚点] 第 2 轮位移 0.25 米（必死 0、锚点 221）
[锚点] 第 3 轮位移 0.10 米（必死 0、锚点 221）
