# usagi 崩塌归因 · 最终结论（八轮迭代闭环）

> 2026-09-15 · 插件 v0.28.0 · 世界 `XIUSAGI`（干净基线副本）· 端口 2466 · 全程无客户端
> **结论：崩塌已完全消除（4625 / 4625 存活，丢失 0）。**

---

## 0. 一句话结论

崩塌的完整因果链是：

```
落点对齐偏差 → 地面锚点只有 33 个 → 支撑沿横向链长距离衰减
→ 石构件的支撑跌破它 100 的下限 → 当帧被销毁
```

**修法：把整栋下沉 1 米，锚点数从 33 拉到 196 个，丢失从 29 件降到 0 件。**

## 2. 关键数据

### 2.1 石构件与木构件的下限差 10 倍

```
构件            数量    初始/最大support    下限    低于下限
stone_pillar     16        1000.0       100.0      0
wood_*          数千         100.0        10.0      0
wood_wall_log   116         140.0        10.0      0
```

**石构件要求支撑 ≥ 100，木构件只要 ≥ 10。**
而支撑链的衰减在正常运行时会把最小值一路压到 **21.7**（观测到的收敛值）：

```
support 最小值: 31.5 → 24.6 → 21.7
```

21.7 对木构件（下限 10）完全安全，对石构件（下限 100）就是**必死**。
**这就是"死的全是石构件、木结构一件不掉"的全部原因。**

### 2.2 传递公式是乘性衰减

`WearNTear.UpdateSupport` 第 930 行：

```csharp
num3 = Mathf.Max(num3, support2 - horizontalLoss * 距离 * support2);   // = support × (1 − loss × 距离)
```

每一跳乘一个小于 1 的因子 → **指数衰减** → 链越长，尾端越低。

### 2.3 锚点数才是真变量（决定性对照）

| YOffset | 盒内命中地形（锚点） | 埋入件 | 贴地件平均间隙 | 丢失 |
|---|---|---|---|---|
| 0 | **33** | 15 | 0.937 米 | **29** |
| −0.25 | 41 | 15 | — | 29 |
| **−1.0** | **196** | **140** | **0.296 米** | **0** |

「盒内命中地形」= 该构件的包围盒（半长 + 0.15 米）里真的含有地形碰撞体，
这是 `WearNTear` 判定"接地"的**唯一**途径（902 行 `flag = true`）。

### 2.4 为什么小位移没用

蓝图的底层**本身横跨约 1.5 米高度**，不是一个平面（贴地件平均间隙 0.937 米）。
偏移扫描显示整体下沉 0.15 米只能把接地件从 23 增到 26 —— **幅度必须到米级才有质变**。

## 3. 逐项排除（都做过实验，不是推断）

| 假设 | 实验 | 结论 |
|---|---|---|
| 蓝图转换出错 | 4625 件全建成、prefab 校验 0 失败；疑似丢件的 `wood_wall_log_4x0.5` 修正脚本后全部在位 | ❌ 排除（那是我的对账脚本缺陷） |
| 地形没整平 | 快照 169 点，建筑下方 166 点全等 39.70；低点在 26 米外 | ❌ 排除 |
| 残留实体（石头/树） | 开 Cleanup 清掉落点 222 个非蓝图对象 | ⚠️ 边际（36→29） |
| 构件悬空、够不着地面 | 冻结磨损后逐件跑游戏同款盒体判定 | ❌ 排除（**0 个孤立件**） |
| 地面贴合度 | YOffset ±0.25 两方向 | ⚠️ 幅度不足，无效 |
| **地面锚点数** | **YOffset −1.0** | ✅ **主因（29→0）** |

## 4. 对上一轮结论的修正

**我上一轮说"地形贴合不是杠杆"是错的。** 错在只试了 ±0.25 米——
那个幅度下锚点只从 33 动到 41，落在噪声里，所以看起来"毫无影响"。
正确幅度是**米级**：33 → 196，丢失 29 → 0。

**你的直觉抓的是因果链的上游，是对的。**
只是"完全一致"的准确说法应该是"**让足够多的底层构件直接接地**"——
不是把地形修得和蓝图一模一样，而是把锚点数拉过临界值。

## 5. 可复用的操作配方

### 判定指标
看 `[激活]` 日志里的**接地件数**（或间隙体检的「盒内命中地形」）：

| 锚点数 | 结果 |
|---|---|
| ~33 | 石构件链尾跌破 100 → 丢 ~0.6% |
| ~196 | 链短到不会跌破 → 丢 0 |

### 调参
```ini
[Build]
## 下沉 1 米：锚点 33 → 196，崩塌 0
## 语义上等价于把 GroundLayerPy 从 -1.60 改成 -0.60
## （两者都只改变"建筑与地形平台的相对高度"，地形平台高度本身不变）
YOffset = -1.0
```

### 不需要做的事
- ❌ **不需要锁支撑**（`Support.Enabled` 可以保持 `false`）
- ❌ 不需要清空自然物（有帮助但非必要）
- ❌ 不需要改蓝图

### 代价
- 底层 140 件埋入土中；对带"裙边/勒脚"设计的蓝图通常是作者本意

## 6. 本轮新增/修复的插件能力（v0.27.x → v0.28.0）

| 变更 | 说明 |
|---|---|
| **修诊断时序** | 原来用固定 1200 帧，而落地要 ~2 分钟 → 每轮只量到 3728/4625，跨轮数据不可比。改成等 `s_buildDone` 标志 |
| **偏移扫描** | 直接算出「下沉 d 米后有多少件盒子能碰到地形」，让"该沉多少"从试错变成查表 |
| **阈值表打全** | 从 16 行扩到 40 行，才拿到 `stone_pillar` 下限 = 100 这条关键数据 |
| 间隙体检 | 逐件测底面→地形间隙 + 跑游戏同款盒体判定 |
| FreezeWear | 冻结 `WearNTear.UpdateWear`，零销毁干扰下量几何（两步法第一步） |

**注意**：冻结磨损时 `UpdateSupport` 不跑，`support` 保持初值（100/140/1000），
所以"冻结下的 support 值"没有参考意义；但 **`下限` 是材料的固有属性，冻结下依然有效**。
